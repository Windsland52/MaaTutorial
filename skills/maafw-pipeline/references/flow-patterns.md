# 流程设计五步法与常用模式

配套 [SKILL.md](../SKILL.md) 工作流第 2–6 步的展开。字段语义以 MaaLLMWiki 路由的 3.1-任务流水线协议为准；文中括号内的版本标注仅作提示，实际支持范围以路由结果为准。

## 第一步：状态清单

把需求翻译成**状态**，不是动作清单：

- 起始态（从哪个界面开始）、每个中间态（经过哪些界面/弹窗）、成功态（怎么算完成）、可能的失败态（断线、公告、加载慢）。
- 每个状态回答"用什么识别"：固定图 → TemplateMatch；文本 → OCR（`expected` 用完整稳定文本）；色块判定 → ColorMatch；无视觉变化 → DirectHit 流程节点；目标尺寸 / 缩放会变导致模板失配 → FeatureMatch（关键点匹配，抗缩放）；模板 / 文本 / 颜色都不可行的复杂目标 → NeuralNetworkClassify / NeuralNetworkDetect（自训 ONNX 模型，官方有训练食谱）；多条件同屏（背景 + 图标等）→ And / Or（v5.3+，v5.7 起支持节点名引用）；以上都表达不了 → Custom 识别（转 `maafw-custom`）。完整名单与字段精确语义以 3.1-任务流水线协议为准。
- 每个状态的证据状态标注 `observed` / `guessed`——有 guessed 就先探索（见 SKILL.md 硬护栏 1）。

## 第二步：主干

起始态到成功态的最短可成功路径排成线性 next 链。每跳一个中间态一个节点；界面切换的等待用"等待目标出现"节点表达，不用长 delay 凑（pre_delay/post_delay 尽量保持默认，加中间过程节点代替等待）。

## 第三步：分支

- `next` 列表顺序即优先级：依次识别，第一个命中立即执行其 action 并进入它的 next。
- **遮蔽约束优先于频次排序**：某候选出现时另一候选也必然命中，前者必须排在前——排反了后者永远轮不到；若被遮蔽的是出口、遮蔽者的动作又消不掉自己的触发条件，直接构成"一直命中"的死循环（`timeout` 救不了，见 SKILL.md 硬护栏 5）。
- 互斥分支用顺序表达，不要靠超时区分；需要"按命中位置/得分/期望文本"排序时用 `order_by`（如 `Expected`）。
- 组合条件用 `And` / `Or`（v5.3+；v5.7 起支持节点名引用）。

## 第四步：循环与中断

完备标准：主线能跑、弹窗能处理、加载能等过去、**不在目标场景时的行为有显式定义**（自动跳过还是失败上报由项目决定）——只通主线不算完成。

- **重复动作**（连点领取、翻页收集）：循环节点 + 出口节点放同一 next 列表，循环体配 `max_hit` 限次防死磕。
- **随时可能弹的界面**：做独立处理节点，以 `[JumpBack]` 前缀挂在关键等待点的 next 列表——命中并处理完后自动回到父节点继续识别；**回跳只在正常态兑现**——异常态下链走空不回跳、任务直接失败（恢复成功后再走空则照常回跳，见 SKILL.md 执行模型）。
- **通用工具节点**：返回键这类高频复用件做成无 next 的 `[JumpBack]` 纯工具节点（如 `BackButton`），挂在多处等待点，处理完各自回到父流程。
- **识别门控自循环重试**：操作可能未生效时，把节点自身放进它的 next（或以 `[JumpBack]` 自引用等待加载）——未生效则同状态再次命中、再执行一次，生效则走到出口。这是"有限重试"的惯用写法，仍需出口节点与 timeout 兜底。
- **跨分支汇合**：`anchor` 记录"最后处理该事件的节点"，后续节点以 `[Anchor]锚点名` 引用。细则：
    - **三种设置形式**：字符串 / 数组锚到当前节点；object 形式（v5.7+）可指定目标节点（`{"X": "TargetNode"}`）或清除（`{"Y": ""}`）；
    - **静默跳过陷阱**：引用未设置 / 已清除的锚点时该候选**被跳过**——锚点必须在所有前置路径上被设置过，审查时专门核对。
- **引用方式三选一（`[JumpBack]` / 节点名 / `[Anchor]`）**。细则：
    - **目标静态已知**：回当前列表用 `[JumpBack]`，指向固定节点用节点名引用；
    - **目标需运行时决定**（共享机件的调用方注入续跑点、多路径各自续跑）才用 anchor——把"未设置即跳过"反过来当条件候选用；
    - **锚点管理纪律**：set / clear 必须显式管理（含退出路径清除），续跑出口列表放兜底候选，防"忘了设锚 → 候选被跳过 → 链走空 → 任务假成功"；
    - **实证形态**：共享"回主界面"机件（调用方入口锚定自己、到家出口 `[Anchor]` 续跑）与共享导航机件的条件续跑族（`[JumpBack][Anchor]X` 组合）。
- **运行时补丁只留给数据，不留给控制流**。细则：
    - **危害**：NodeOverride 类机制改 `next` / `enabled` / 选哪个节点，会让静态 JSON 的控制流图说谎——审查与检索以静态文件为唯一真相；
    - **替代手段**：这类逻辑用静态双路径（变体各自成节点）或锚点续跑表达；
    - **正当领地**：仅"参数值取决于运行时观测"（OCR 读数 → 次数）才是 custom override 的领地；
    - **动机案例**：某刷本任务的运行时四连补丁——`enabled:false` 应为 `max_hit:1`，next 重接应为锚点续跑，倍率字段改写应为静态双节点，仅动态次数该留 custom。

## 第五步：失败路径

- 每个 next 列表问"全没命中怎么办"：`timeout`（缺省 20000ms；`-1` 无限等待慎用，v5.5+）+ `on_error` 兜底（回退节点/重试入口/上报停止）。
- 动作执行失败同样进入该节点 `on_error`。
- 重试骨架：独立重试节点 + `max_hit` 限次；不要用 timeout 拉满代替重试设计。
- **重试是安全带不是修复**（拒绝两类重试）：
    - **死循环式**——失败原地再试直到超时；
    - **掩盖式**——A 失败换 B、B 失败换 C，根因永远找不到、问题无法定位；
    - 「点击没反应就**盲目**再点一次」是典型禁手——第二次点击可能已作用于下一界面的其他元素；正确做法是先 `pre_wait_freezes` / `post_wait_freezes` 等画面静止，或加"重新识别到按钮仍在才再点"的有限重试。
- **区分设计期安全带与事后补丁**：循环体设计时就配 `max_hit` 限次是安全带（见第四步）；跑出死循环后为压症状补 `max_hit` 是补丁——死循环几乎都是识别问题或逻辑缺陷，硬中断只会掩盖（如同在代码里盲目抛异常跳出任务）。确属无解的场景（游戏动画卡死、网络抖动）经确认后才允许有限次重试。

## 模式示例

```jsonc
{
    "EnterBattle_Start": { "next": ["Wait_MainMenu"] },
    "Wait_MainMenu": {
        "next": ["EnterBattle_InMenu_StartButton"],
        "timeout": 30000,
        "on_error": ["Wait_MainMenu_Error"]
    },
    "EnterBattle_InMenu_StartButton": {
        "recognition": { "type": "OCR", "param": { "expected": "开始行动", "roi": [/* 实测量取 */] } },
        "action": { "type": "Click" },
        "next": [
            "[JumpBack]Announcement_Close",
            "Wait_InBattle"
        ]
    },
    "Announcement_Close": {
        "recognition": { "type": "TemplateMatch", "param": { "template": "MainMenu/AnnouncementClose.png" } },
        "action": { "type": "Click" }
        // 无 next：节点链走完，JumpBack 生效，回到"EnterBattle_InMenu_StartButton"重新识别 next
    }
}
```

> 示例为 **v2 嵌套写法**（`recognition` / `action` 收敛为 `{type, param}`，v4.4.0+），与 v1 扁平写法字段语义等价、引擎逐节点兼容。**新建项目默认 v2**，理由：识别 / 动作 / 流程三组参数的命名空间分开，参数塞错组在结构上不可发生（v1 的错位字段被静默忽略、不报错——对 LLM 编写是最大暗坑）；schema 可按 `type` 精确校验；与 `default_pipeline.json` 的类型对象结构同构。存量项目跟随既有主流风格、不必整仓转换；两种写法混用合法但应项目内统一（社区存量 v1 / v2 均有主力，混写常见）。

生成完先自查可达性（孤立节点、anchor 断链、未解析引用），再做单节点验证与端到端验收（转 `maafw-debug`）。

## 稳定性法则（社区实证）

- **识别 → 操作 → 再识别**：每一步操作都基于识别——操作后的画面必须重新识别确认，不允许沿用操作前的认知。推荐"识别 A → 点击 A → 识别 B → 点击 B"；**禁止**"整体识别一次 → 连点 A/B/C"。跳过"再识别"会踩两类坑，治法都是多加一个"操作已生效"的确认节点：
    - **画面已变，点错**：点完跳转/关闭按钮后界面不可保证——极端情况下游戏弹出新池子公告，直接点下一节点可能点进抽卡里。正确链路：识别跳转按钮 → 点击 → 识别"界面已跳转完成"。
    - **画面未变，白点**：跳转可能还在后台加载导致画面卡住，点击可能没与服务器成功交互（用户网络不保证顺畅），界面卡死怎么点都没反应。正确链路：识别提交按钮 → 点击 → 识别"提交成功"——会更改账号数据的按钮尤其必须确认。
- **少用硬延迟，但不禁止**。细则：
    - **默认不加**：延迟常在掩盖问题——用户设备存在高延迟时依然不会稳定；优先中间识别节点与 `*_wait_freezes`（`target` 指向预期新界面的特征区域并配 `time`，等该区域静止而非整屏；其 `timeout` 默认 20s——目标区域有持续动画时等满才继续，常配 1~2s 兜底）；
    - **合法场景**：过渡动画无可识别的中间状态、需要控制操作节奏（防检测 / 冷却）、实测个别设备不稳——用小值 `pre_delay` / `post_delay` 并在 desc 注明原因；
    - **红线**：不要用大值延迟代替等待设计。
- **on_error 只做异常恢复**：不把 on_error 用作正常流程的一部分（例如实现 if-else 的分支效果）——它只承担错误后的回退/重试/上报。
