# Custom 实现决策指南

通用层只规定**契约与判据**。回调参数 / 返回值的表达、对象与图像数据的生命周期、异常跨界行为、同步异步与线程约束、当前版本暴露哪些 Context / Agent API——这些都随 binding 与版本不同，确定项目所用 binding 后回源核对（路由 MaaLLMWiki 的 bindings / native-api 索引），不在本文硬编码。实证样例仅在解释易误解的机制时出现。

## 注册与加载

**要解决的问题**：实现如何被宿主发现并完成注册，且发生在任何 pipeline 调用与连接待命之前。

- **判据**：注册代码放哪（实现处就近声明 / 入口集中调用）只是位置选择，不互斥、不绑语言与规模；真正要回答的是——谁保证实现被**加载执行**、注册恰好一次、注册名全局唯一、注册关系可审计。
- **不变量**：
    - 实现模块必须被实际加载执行——**文件存在 ≠ 注册完成**（样例：Python 装饰器注册在定义模块被 import 后才发生，入口需要确定的实现模块加载清单）；
    - 注册名全局唯一、大小写敏感，是 pipeline ↔ 实现的唯一契约；
    - 注册关系可审计——集中注册天然一处可见；就近声明则必须有确定的加载清单兜底；
    - agent 子进程模式：注册在连接建立、进入待命之前完成。
- **常见失败**：实现写好但不在加载清单里——pipeline 引用时静默缺件；同名注册大小写不一致；注册晚于连接。
- **验证**：注册冒烟——启动即列出 / 日志确认全部注册名，再接 pipeline 引用。

## 模块边界

**要解决的问题**：实现代码按什么单位组织、共享代码何时抽离。

- **判据**：按**业务能力**组织（一个业务的识别 / 动作 / 辅助逻辑聚在一处），与 resource 的模块目录**同名对齐**——对齐的是"能力 ↔ 模块"映射，目录名与文件粒度随语言惯用法，不设统一规定；共享件被 ≥2 个业务复用才抽到独立共享层，不提前抽。
- **不变量**：业务实现不反向依赖注册基础设施内部；共享层不依赖具体业务。
- **常见失败**：按技术分层平铺（全部识别一目录、全部动作一目录）——单业务改动跨多文件；共享件抽早了变双向依赖。

## 参数契约

**要解决的问题**：pipeline JSON 与实现之间的参数接口稳定、可校验。

- **判据（分层取用）**：
    - **底线（一切项目）**：类型、必填、默认值、错误行为明确；入口处统一解析与运行时校验，解析逻辑独立成可测函数；
    - **有 Schema 基建**：参数结构入 Schema、注册名入 enum、接进项目**实际校验入口**——建文件本身不产生校验；
    - **规模增长后**：再上集中注册表与自动同步。
- **不变量**：未知 / 非法参数显式失败，不静默吃默认值混过。
- **常见失败**：裸取字段——拼错参数名拿到空值，到设备上才炸；Schema 与注册名单独维护、改删不同步。

## Pipeline 复用

**要解决的问题**：custom 内需要识别 / 动作时，何时复用既有节点、用哪一帧、怎么判结果。

- **判据**：
    - 优先按节点名引用既有 pipeline 节点跑识别（识别逻辑单一真相），只在其字段表达不了时才在代码里写判定；
    - 图像来源按用途：识别回调判定本次画面用**回调传入的图像**；动作后要新画面经既有 controller 主动截图——**截图完成与取图是两步**（只等不取，取到的仍是旧缓存；等待画面静止的原语内部连续截图，返回后缓存也是新的）；**最近缓存**（属 controller，不会自己刷新）仅在时效可接受时用；不另建截图 / 控制器链路；
    - 结果判定看该次调用的返回（命中与否 / box / detail），不复跑第二遍确认。
- **不变量**：不复制既有节点的识别逻辑成代码；不用过期缓存冒充操作后画面。
- **常见失败**：拿最近缓存当"当前帧"做操作后验证；代码里手写模板匹配，与 pipeline 节点日渐漂移。

## 状态与作用域

**要解决的问题**：跨调用需要记忆时，状态放哪一级、谁清理。

- **判据——按四档选最小够用**：
    - **单次回调内**：局部量，天然清理；
    - **单任务内**：实现侧状态，任务入口显式初始化；
    - **进程内跨任务**：随宿主 / agent 进程存活共享——任务重入带着上次的值，生命周期必须显式（重置点、清理点）；
    - **持久化**：文件 / 数据库，跨次运行——格式与迁移自己负责。
- **不变量**：任何跨回调状态都有显式生命周期说明与清理责任；传数据不向控制流打补丁——override 用时写明对象与作用域，四条边界坑：`override_pipeline` 校验失败**不回滚**（逐 key 写入后才校验）；`override_next` 会把节点当前定义**物化**为补丁快照、节点不存在即调用失败（返回值要判）；`run_task` / `run_recognition` / `run_action` 的逐次 override 落在克隆上、不持久（也不能向父流程回传）；控制流改写的正当性边界见 maafw-pipeline 的 flow-patterns。
- **常见失败**："只跑一次"哨兵跨任务污染；拿 override 当父子流程的数据通道。

## 失败与取消

**要解决的问题**：未命中、动作失败、实现异常、停止请求各自正确的处理。

- **判据**（语义详见 SKILL.md 硬护栏 2 / 4）：
    - 未命中 = 本候选不命中，轮询继续；整轮未命中走宿主超时与 on_error；
    - 动作失败 = 走动作节点 on_error；实现异常不吞、显式失败返回；
    - 停止请求：框架不会主动打断回调——长循环自查停止条件、外部 IO 设超时、清理用 finally / RAII 等该语言机制。
- **不变量**：四种情况各有可观测出口（返回值 / 日志 / on_error 至少其一）。
- **常见失败**：把候选未命中当失败上报；阻塞循环无停止检查，拖死整个任务。

## 事件监听（Sink）

**要解决的问题**：哪些逻辑属于观测与通知，哪些必须进显式执行路径。

- **判据**：横切钩子接两条既有 sink 通道——**Tasker sink 收任务级成败**（载荷就是任务的 Starting / Succeeded / Failed），**Context sink 收节点与动作级事件**（focus 消息也在这条通道）；对所有任务 / 节点统一生效的关注点（截图体检、失败后的用户引导）→ sink，单节点业务 → Custom。展示与上报的**落地在 Client**（GUI 状态、interface.json `telemetry` / `focus.trace`——框架只内置事件与状态查询，且可被用户开关否决）——sink 里只做项目特有反应，不重造上报。注册入口随形态：进程内经 Tasker / Context 的 add_sink，agent 子进程内经 AgentServer 的 add_*_sink（Remote 实例不支持 add_sink）。另注意 `run_task` 子任务不发任务级消息，要在 sink 里观测父子任务需知此差异。
- **不变量**：Sink 只观测与引导，不改业务流程的执行结果。
- **常见失败**：把统一检查复制进每个动作；在 Sink 里做业务决策（该走 pipeline / custom 的控制流）。
- **机制样例**：实证项目的 `taskfail`——稳定任务失败时按 entry 名单弹反馈指引、引导用户去 issues（观测与引导，不是上报通道；上报走遥测 / GUI 内置）。

## 验证

分层推进，每层失败定位面最小：

- **参数单测**：解析 / 校验函数独立可测（非法参数、缺省路径）；
- **注册冒烟与最小节点闭环**：即 SKILL.md 工作流 3（「注册与加载」节末另有验证行）；
- **单节点流程与设备端到端**：截图 + 期望结果判定、验收层四问——转 `maafw-debug`。

## 实证附注（规则来源，非运行时指令）

本文判据蒸馏自活跃社区项目（单语言 Python agent 与多语言 Go service 两类形态），样例已隐名；目录树、注册表实现、命名后缀等项目特有形态不构成规范，遇到同类需求按本文判据、以所用语言的惯用法落地。
